# 技術ブログ記事のレビュー

指摘は以下の4段階に分け、順に修正

1. 主張 : 主張が1本に通っているか
2. 枝葉 : 章の中身が幹を支えているか
3. 誤り : 誤字脱字、製品名、不可視文字
4. 表記ゆれ : 括弧、句点、漢字かな

段階を分けるのは、一度に全部出すと著者が取捨できず、結局どれも直らないため
勝手に直さない。提示→承認→反映。記事は著者の声なので、善意の修正が語り口を壊す

## 最初に確認すること

レビュー前に、記事の想定読者と目的を確認。同じ記述が、読者次第で欠陥にも狙い通りにもなるため

* 記事内の想定読者の章を使う。無ければ著者に聞く
* 専門用語、前提知識の省略、説明の厚さは、想定読者次第
  * 同業者向けなら専門用語の羅列は成立。入門者向けなら 3 相当の欠陥

## 進め方

* 1, 2 は1件ずつ相談して反映。追記が必要で、著者の意図を確認しないと方向を誤るため
* 3, 4 は承認後に一括反映。機械的に判断でき、個別確認が不要なため
* 公開済み記事は 3 だけでも価値あり。1 は章の入替や削除を伴う大手術で、割に合わないことも
  * その場合、1 は「次の記事へのフィードバック」として残し、記事は触らない
* 意図の読めない表現は「指摘」でなく「意図か確認」で出す。著者の狙いを誤って潰さないため
  * 記事内で唯一の強調、専門用語だらけの章、宣伝や採用の文、崩した語り口など

## 1 : タイトル/章立ては妥当か : 記事の主張=幹は何か？記事はその幹に対して一貫しているか？

幹の一貫性をまず定めないと以降の指摘が無駄になるため、最初に見る

* 記事の幹は何か？
  * 唯一の主張したい事=幹は何か。冒頭で提示されているか
  * タイトル, 結論/まとめ趣旨は、その主張と一致するか
* 章立ては妥当か？
  * 上記の主張を説明するための章立てとして妥当か？
  * 章立ては、結論から始まり、粒度が徐々に詳細化する流れにすること
    * 全体を示さないまま、深掘りが入ると読み手は迷子になる
* 各章の主要なメッセージは上記幹と整合しているか？
  * 結論/まとめは本文から導けるか。本文に無い主張が出ていないか
  * 各章は結論に寄与するか。しない章は appendix 送りか削除
  * 「書くこと/書かないこと」の宣言と本文のズレ

検証 : 各章の冒頭1行だけを並べ、結論に辿り着くか見る。辿り着かない章が削除か追記の候補

## 2 : 枝葉 : 章の中身は幹を支え、邪魔していないか？

1 で明確化した幹に対して、章の中身＝枝葉がそれに整合するか。枝葉は読み飛ばせてよいが、幹を矛盾したり邪魔してはいけない

* 枝葉が幹と矛盾しないか
  * 表現の矛盾
    * 例 : 「ノーコードです。インフラコードは書いてます」
  * 章の中身が、その章の冒頭メッセージと合っているか
* 枝葉が幹を邪魔しないか
  * 章のメッセージに寄与しない段落や長い脱線が挟まっていないか。挟まっていれば appendix 送りか削除
  * 前提の説明が無い。本文で使う製品や用語が、何かを説明されずに登場する
* 枝葉が単独で辿れるか。読み飛ばさず読んだ人が詰まらないか
  * 画像と説明文の対応。「このように」がどの画像を指すか
  * 真似できないプレースホルダ。真似する読者が一番詰まる箇所で、優先度高
  * 本文から辿れない指示語
  * URL の重複掲載

## 3 : 誤り

読者に誤情報を渡す、または著者の信頼を損なうもの。公開済みでも直す価値あり

* 誤字脱字、語の重複
  * 例 : 「頑張ってもらってもらいます」
* 製品名の正確さ
  * ベンダー名の取り違え（Amazon と AWS など）
  * 大文字小文字（Eventbridge、lambda、claude）
  * スペース抜け（AmazonQ）
  * 製品名は検索語そのもので、誤ると記事に辿り着けない
* コード内コメントの自己矛盾
  * 例 : 変換前後を示すコメントの左右が同じ文字列
  * コードは読者がコピーして動かすため、矛盾は実害
* 不可視文字の混入
  * NBSP（U+00A0）。管理画面や PDF からのコピペで入る
  * 見た目で気づけず、読者のコピー時に壊れる
  * 検出 : `python3 -c "import io,sys;s=io.open(sys.argv[1],encoding='utf-8').read();print(s.count(chr(0xa0)))" FILE`
* 記事内の自己矛盾
  * 同じ語の別表記どうしを突き合わせる

## 4 : 表記ゆれ

必ず最後。1, 2 の書き直しで再発するため

原則は「記事内で多い方に揃える」。固定ルールだと、著者が意図して崩した箇所まで潰す

| 種類 | 揃え方 |
| --- | --- |
| 括弧 | 日本語文中は全角、コード内の英文は半角 |
| 句点 | 行末は無し、行中は有り。コードブロック内は対象外 |
| コロン | 半角 ` : ` か全角 `：` に統一 |
| 読点 | 日本語文中の半角カンマを読点に |
| 記号 | チルダ（`$3~$4`）、矢印（`->` と `→`）の混在 |
| 漢字/かな | 出来る→できる、事→こと、達→たち |
| スペース | 日本語と英数の間の有無 |
| 箇条書き | 記号の有無。参考文献だけ素のリンク等 |
| 見出し | 体言止めか文か |

行末の句点を書かないのは、改行が `<br>` になる媒体では改行が文末を示すため。句点は情報を足さない

## Zenn 固有

媒体が変われば、この章だけ差し替え

* 生 HTML 不可（サニタイズされる）。画像の横並びは表で
* 画像サイズは `![alt](url =180x)`
* 改行はそのまま `<br>`
* 画像 URL が `raw.githubusercontent.com` なら、記事より先に push
* 連続画像は別ブロックになるため、キャプション行で対応づける

## 参考文献

* 公式ドキュメントを優先
* URL は実在確認の上で書く。推測リンクは記事全体の信頼を落とす
* 著者の過去記事は入れない。本文中のリンクなら可
* 本文中のリンクとの重複を避ける

## 指摘の語調

断定と提案を使い分ける。誤りと好みが同じ強さで並ぶと、著者が取捨できないため

* 1, 2 は提案（「〜すると伝わる」）。判断は著者に残す
* 3 は断定（「〜が誤り」）
* 4 は事実の提示（「〜と〜が混在」）

## 出力テンプレート

必ずこの形で出す

```markdown
（結論を1-2行）

## 1 : 主張
（行番号つきの箇条書き）

## 2 : 枝葉
（行番号つきの箇条書き）

## 3 : 誤り
| 行 | 現状 | 指摘 |
| --- | --- | --- |

## 4 : 表記ゆれ
| 種類 | 混在の状況 |
| --- | --- |

## 自己反論2-3つ
* 反論1「（指摘を否定する仮説）」→（検証結果）
* 反論2「（同上）」→（同上）

（どれから直すかを質問して終わる）
```

指摘は具体的に。行番号と現状の文字列を必ず添える

例 :

* 悪い : 製品名の表記を統一してください
* 良い : 32行目 `AWS GuardDuty Investigation Agent` → タイトルと207行目は Amazon なので不一致

## やらないこと

* 承認前の修正
* 意図的な表現への指摘
* コードブロック内の文体統一。稼働中の設定を見た目のために書き換えると、読者と著者の手元がズレる
* 一括置換。語り口を壊すため、行単位で確認
* 4 の先行。上流の書き直しでやり直しになる
